# 雙層任務理由分析手冊

版本scenario-reasons-v3，2026年11月16日。這份手冊取代舊理由手冊作為新版兩層任務的開發分析規則。尚無新LLM回覆，因此沒有行為分類結果或真人編碼一致性；先導後若需修改定義，須新增版本並重新編碼受影響資料，不能事後只調整想要的案例。

## 分析目的與單位

觀察不同情境下，LLM的協助選擇與陳述考量是否改變。每筆可讀、非重複的原始理由為一個單位，動作、理由與品質判斷分開。分析文字中說了什麼，不推論隱藏思考、真實人格、利他心理或因果機制。重複呼叫同一模型不是不同真人受試者。

抽象效用任務使用原報酬表；物理任務使用布局或開發時間預測。兩者分組分析，診斷與自由選擇也不合併。提供預測資訊與只提供布局的差異屬資訊條件差異，不直接解釋為同資訊下推理能力差異。

## 十二個可並存標籤

| 代碼 | 中文意義與納入判準 | 排除或邊界 |
|---|---|---|
| personal_cost | 個人代價與自身效益，使用自己的報酬、負擔或較早撤離作選擇比較 | 只抄cv或時間數字不算；沿用舊代碼但涵蓋個人收益比較 |
| avoid_unhandled_loss | 以無人協助的後果為理由 | 泛稱幫忙很好不算 |
| reliance_on_others | 以他人可能接手、拒絕或已明確給定的意願背景為理由 | 只列人數不算；推測與已知承諾須分開 |
| shared_benefit | 使用其他人的撤離結果或共同通行效益 | 自己較快離開不自動等於關心他人 |
| guaranteed_payoff | 明確偏好固定報酬或最差情況保障 | 原報酬固定不等於物理時間保證；實體任務中的錯誤保證另標資訊問題 |
| context_use | 將提供的τ、X、M或布局連結到選擇 | 只重述參數不算；不得自行把M說成重量或秒數 |
| forecast_use | 使用已提供的校準預測或其比較 | 只在物理診斷或calibrated_forecast成立；布局組猜時間不是使用所提供預測 |
| uncertainty_awareness | 明確承認他人行動未知、預測有變異或不保證結果 | 單純使用may一字但未表達資訊限制時，依完整語意判讀 |
| scale_or_normalization | 討論效用比例、數值尺度或301正規化對取捨的意義 | 只抄公式不自動算選擇考量 |
| unsupported_assumption | 把沒有提供的承諾、出口、受傷、期限或成功當已知 | 明確標示不確定的信念不自動算捏造，但不能以猜測當事實 |
| action_reason_conflict | 理由明確主張另一個最終動作，與raw decision相反 | 同時描述利弊或猶豫不算，語意不清時記unclear |
| insufficient_reason | 沒有可辨識的考量支持選擇 | 短但有理由不算；文字非空不等於理由充分 |

每個標籤都需附上原理由的精確quote及start/end位置。位置以Python的Unicode codepoint計算，start含起點、end不含終點，不能用Unity UTF-16索引直接替換。可以共用同一句支持多個標籤，但每個標籤都要明確綁定證據。

標籤記錄的是陳述考量，即使考量使用了錯誤資訊，也可同時標personal_cost與unsupported_assumption。出現標籤不表示該理由正確。只有一句泛泛的動作宣告時，標insufficient_reason而非自行補出動機。

## 兩層任務的判讀差異

抽象報酬下，協助得到固定1−cv，可合理陳述確定報酬。沒有給定他人機率時，不能因cv<av就評定協助是唯一正確選擇；同樣不能把拒絕當錯誤。若模型自己推測別人可能接手，記其信念，不當已測得機率。

物理預測下，六種子的平均與觀察範圍不是本輪保證。把平均說成必然發生，或把全部其他人願意當成至少一人願意，須檢查unsupported_assumption。τ=0代表相關出口完全阻塞，不能再推論事故、死亡或搬不動。接近及搬運投入不等於淨撤離延後，M也不是總搬運時間。

若布局組說「我可能需要更多時間搬運」，可記個人成本考量；若說「確定多花20秒」而未提供這個數值，應另記資訊問題，不能標成forecast_use。提供預測組若引用表中的時間，才有資格標forecast_use。工具只檢查這個資訊條件界線，不能取代語意判斷。

## 四個獨立品質欄位

每筆已覆核理由須填actionReasonRelation、comparisonJudgment、unsupportedInformation及arithmeticJudgment。可用值見機器版手冊；unclear必須附註，不能當通過。

actionReasonRelation為consistent、conflict或unclear，檢查理由支持的最終選擇，不是檢查該選擇是否最有效。conflict需同時有action_reason_conflict標籤及原文證據，原動作仍保持不變。

comparisonJudgment用於理由中的明確比較是否成立。診斷有預定比較題，必須判correct、incorrect或unclear；自由選擇沒有唯一效用最優答案，可填not_applicable，或只評理由中能核對的明確比較，不把整個選擇評成對錯。

arithmeticJudgment只評明確算式，不能因文字不喜歡就標算錯。comparison或arithmetic為incorrect時，必須有錯誤原文片段及說明。沒有數值計算可填not_applicable。unsupportedInformation為none、present或unclear；present須有unsupported_assumption標籤。unclear是待釐清，不能被自動當作矛盾或捏造。

## 全量保留與分母

編碼表保留登錄中的全部列，包括尚未呼叫、只有claim、HTTP或格式無效、重複provider回覆。這些列不會被填上推測理由。模型回覆格式可讀但診斷選錯，保留為semantic_failure並仍可分析理由，不因答案錯就刪除。

摘要依phase、scenario、information分組，逐組報planned、記錄狀態、可讀非重複理由、已覆核及未覆核數量。標籤比例分母是該組已覆核且可分析的理由，未覆核數須同時呈現。零覆核時比例為null，不寫0%。多標籤比例不必加總100%。不同階段與資訊條件不得混成單一比例。

代表例子在每組、每個標籤內依trialID字典序，選第一筆已覆核正例與第一筆未具該標籤的已覆核例。後者只是標籤缺席，不能說它證明相反動機。完整理由與編碼另保留，不只發表漂亮句子；語意衝突、錯誤及反向結果也保留。

## 覆核流程與版本

先由工具從raw檔建立表，預設全部unreviewed且沒有標籤。逐筆閱讀提示、觀測、動作與理由，添加標籤、證據、品質判斷、編碼者姓名及類型、note。不能手動改rawAction、reasonText或情境。工具驗證原文與雜湊，不透過關鍵字自動替模型判動機。

本階段未使用另一個LLM分類，也沒有第二位真人編碼者。若之後增加分類LLM，需保存模型、提示、原始分類輸出及覆核紀錄；LLM標註不是人類真值。沒有獨立第二位真人就不報人類一致性、kappa或真人效度。能隱藏條件時盡量隱藏，但文字本身透露條件，不能宣稱完全盲化。

若手冊需要改版，保留舊版及其雜湊，建立新表並重新編碼受影響資料。正式分析前須凍結實際使用版本；本版是先導前的可執行開發規則，不是假稱已完成正式登錄。

## 診斷放行與第3步的銜接

gate-review轉接器只接受完整覆核的診斷，不接受自由選擇當正確答案測驗。所有登錄診斷須可讀、非重複、無錯誤動作，理由比較正確、動作一致、沒有未解資訊問題；算術需正確或不適用，且不能只是空泛理由。

轉接檔帶回第3步所需的raw雜湊、原文、動作與具名覆核，不更改原結果。最後仍由第3步transport重讀live證據判定能否放行。合成測試就算填完表，也不能變成live語意通過。

這些是軟體與證據結構要求。工具無法證明人工標籤語意正確，不能把「程式檢查通過」寫成「理由已客觀驗證」。
